# Бэкенд вопросов и консультаций

Сервис сохраняет обращения в SQLite и отдает сайт с того же адреса. Форма показывает успех после записи в базу. Почтовая программа больше не нужна для отправки. В `/admin/` команда может искать обращения, менять статус, оставлять заметки и выгружать CSV.

Это бэкенд публичного сайта. Учетные записи, уроки и платежи самой платформы TeacherDesk остаются во внешнем приложении. Отправка уведомлений на почту, в Telegram и CRM пока не подключена: новые обращения нужно смотреть в панели.

## Локальный запуск

Все команды выполняются из корня репозитория, где находятся `README.md`, `site/` и `server/`. Для локального запуска нужен Python 3.9 или новее, дополнительные библиотеки не нужны.

```sh
python3 -m server.manage init-env
python3 -m server --host 127.0.0.1 --port 8131
```

Открыть `http://localhost:8131/`, панель - `http://localhost:8131/admin/`. Секретный ключ `ADMIN_TOKEN` находится в созданном файле `.env`; откройте этот файл в редакторе и введите ключ в панели. `init-env` никогда не перезаписывает существующий `.env`.

Ключ передается в заголовке `Authorization: Bearer ...`, хранится только в памяти открытой страницы и очищается при выходе или перезагрузке. В адресную строку и браузерное хранилище он не записывается. Чтобы отозвать доступ, замените `ADMIN_TOKEN` в `.env` и перезапустите сервис. Без ключа закрытый API недоступен.

Данные сохраняются в `server/data/requests.sqlite3`. Перезапуск не очищает обращения. `.env`, базу и резервные копии нельзя помещать внутрь `site/` или добавлять в публичный репозиторий.

## Перенос на сервер через Docker

Архив текущего сайта и сервера без базы, секретов и рабочих материалов можно собрать командой `python3 deploy/package.py ../teacherdesk-server.zip`. Команда не перезаписывает существующий архив. В архив попадает текущая папка `site/`; это не заменяет приемку контента или релизную сборку. Файл `.env` и существующие обращения переносятся отдельно по инструкции ниже.

1. Передайте папки `site/`, `server/`, `deploy/` и файлы `Dockerfile`, `compose.yaml`, `.dockerignore`, `requirements.txt`. Генератор `build/` для запуска не нужен.
2. На сервере создайте личный `.env` командой `python3 -m server.manage init-env`. Можно создать файл на своей машине и передать его отдельно по защищенному каналу. `.env.example` содержит только пример настроек.
3. Укажите в `.env` `PUBLIC_ORIGIN=https://teacherdesk.ru`. Если перед сервисом установлен nginx из `deploy/nginx.conf`, установите `TRUST_PROXY=true`. Для обращения напрямую к локальному сервису оставьте `TRUST_PROXY=false`.
4. Запустите сервис:

```sh
docker compose up -d --build
docker compose ps
curl --fail http://127.0.0.1:8131/api/health
```

Сервис слушает только `127.0.0.1:8131` на сервере. Настройте HTTPS в nginx: образец `deploy/nginx.conf` направляет сайт, `/api/` и `/admin/` в этот сервис. Сначала выпустите сертификат на свой домен, замените домены и пути сертификатов в образце, проверьте `nginx -t`, затем перечитайте конфигурацию nginx. Нужен обычный сервер с Python или Docker; статический хостинг без серверного процесса не принимает формы.

В Docker база лежит в именованном томе `teacherdesk_teacherdesk-data`, внутри контейнера - `/data/requests.sqlite3`. Том переживает пересборку образа и `docker compose down`. Команда `docker compose down -v` удаляет том вместе с обращениями. Контейнер запускается без root, файловая система образа доступна только для чтения, запись разрешена в `/data` и временную папку.

Для обновления кода повторите `docker compose up -d --build`. Для просмотра ошибок: `docker compose logs --tail=100 app`. В журналах нет содержимого форм и ключа панели.

## Запуск без Docker

Для сервера предусмотрен Gunicorn. Используйте отдельного системного пользователя `teacherdesk`, каталог `/var/www/teacherdesk` и Python 3.10 или новее (требование Gunicorn). Владелец `server/data/` должен иметь право записи. Пример команд из каталога проекта:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m server.manage init-env
mkdir -p server/data
.venv/bin/gunicorn --config deploy/gunicorn.conf.py server.app:application
```

Для автоматического запуска установите `deploy/teacherdesk.service` в systemd, проверьте пользователя и пути, включите сервис и настройте nginx так же, как для Docker. По умолчанию Gunicorn слушает `127.0.0.1:8131`; переменная `BIND` меняет адрес. Встроенный `python3 -m server` предназначен для локальной проверки.

Конфигурация использует один процесс и четыре потока: ограничитель частоты обращений общий для потоков одного процесса. Не увеличивайте число процессов или реплик без общего ограничителя и пересмотра работы с базой. При перезапуске процесса счетчики ограничителя сбрасываются.

## Резервная копия и восстановление

SQLite нужно копировать через backup API, чтобы получить согласованную копию при работающем сервисе. CLI делает именно такую копию и отказывается перезаписывать существующий файл.

Локально или при обычном запуске:

```sh
python3 -m server.manage backup backups/requests-2026-10-28.sqlite3
```

В Docker создайте копию в томе и заберите ее на сервер. Каталог `backups/` на сервере предварительно создайте с доступом только владельцу:

```sh
mkdir -m 700 -p backups
docker compose exec -T app python -m server.manage backup /data/requests-backup-2026-10-28.sqlite3
docker compose cp app:/data/requests-backup-2026-10-28.sqlite3 backups/requests-2026-10-28.sqlite3
chmod 600 backups/requests-2026-10-28.sqlite3
```

Меняйте имя для каждой копии. Сохраняйте копии отдельно от рабочего сервера. CSV служит для работы с обращениями; для полного восстановления нужна копия SQLite.

Восстановление выполняется при остановленном сервисе. Сначала сохраните текущее состояние всей папки данных отдельно, включая `requests.sqlite3-wal` и `requests.sqlite3-shm`, если они есть. Затем замените рабочую базу проверенным файлом резервной копии. Старые `-wal` и `-shm` не должны оставаться рядом с восстановленной базой. Восстановите владельца файла и права `600`, запустите сервис и проверьте панель. Для Docker изменяйте содержимое именованного тома при остановленном `app`; владельцем должен быть UID/GID `10001:10001`.

Для переноса существующих обращений используйте этот же порядок: backup на старом сервере, передача копии, восстановление на новом до запуска публичного трафика. Не копируйте только основной файл работающей SQLite через Finder, `cp` или `docker cp`: незаписанные изменения могут находиться в WAL.

## Формы и подключение регистрации

Вопросы и консультации принимает `POST /api/requests` с JSON. Поля: `kind` (`question` или `consultation`), `name`, `phone`, `email`, `question`, `preferred_contact` (`any`, `email`, `phone`), `consent`, `news`, `website`, `source_path`, `source_tag`. Нужны имя и хотя бы один контакт; для вопроса обязателен текст, для консультации он необязателен. `consent` должен быть `true`, рассылка включается только явно через `news=true`.

Форма содержит скрытое поле от простого спама, повторная отправка одного запроса с тем же `Idempotency-Key` не создает дубликат. Сервер проверяет типы и длины полей, ограничивает размер JSON до 16 КиБ, отклоняет чужой Origin и частые отправки. Эти ограничения рассчитаны на небольшой публичный сайт. За доверенным nginx клиентский IP берется из замененного заголовка `X-Forwarded-For`.

Кнопки консультации можно подключать атрибутом `data-consult-open`; также доступна ссылка `/#consultation`. Массовое добавление кнопок в страницы выполняется отдельно. Текущая кнопка `data-ask-open` открывает вопрос.

`REGISTER_URL` и `LOGIN_URL` в `.env` задают назначения серверных переходов `/register` и `/login`. Их также отдает `GET /api/public-config`: скрипт сайта обновляет существующие кнопки регистрации и входа после загрузки страницы. Когда новая страница регистрации будет готова, обновите эти переменные и перезапустите сервер. Пересборка для этого не нужна. В статическом HTML резервным адресом остается `app.teacherdesk.ru`; при отключенном JavaScript используются эти адреса. Саму регистрацию этот сервис не выполняет.

Закрытый API панели:

| Метод и адрес | Назначение |
| --- | --- |
| `GET /api/admin/requests` | Список, поиск и фильтры `status`, `kind`, `q`, `limit`, `offset` |
| `PATCH /api/admin/requests/{id}` | Статус `new`, `in_progress`, `closed` и внутренняя `note` |
| `GET /api/admin/requests/export.csv` | CSV с теми же фильтрами, защищенный от формул в пользовательском тексте |
| `GET /api/health` | Проверка доступности сервиса без раскрытия обращений |

## Перед открытием сайта

Проверьте в своем домене отправку вопроса и консультации, появление обеих записей в панели, изменение статуса и скачивание CSV. Перезапустите сервис и убедитесь, что записи сохранились. Проверьте резервную копию на отдельном экземпляре.

Юридические страницы в текущем реестре отмечены как примеры. До релизной сборки проверьте их содержание и публикацию: форме нужны работающие ссылки на согласие и политику, а опциональной рассылке - страница согласия на рассылку. Остальная проверка страниц, SEO и переезда описана в [памятке сервера](pamyatka-servera.md).

Проверка текущей релизной копии выявила 30 битых ссылок: в основном на удаляемую `/consent/`, а также на примеры договора, базы знаний и повторяющихся уроков. Эти статусы контента не менялись при добавлении бэкенда. Обычная сборка для просмотра проходит и сохраняет документы. Архив переноса содержит эту версию для просмотра, поэтому перед открытием сайта нужна завершенная релизная проверка.

## Проверка серверной части

`python3 -m unittest discover -s tests -v` запускает интеграционные проверки во временных базах и тесты экспорта Pages. Для бэкенда проверены сохранение после перезапуска, валидация, одновременные повторные отправки, ограничения частоты, доступ к панели, фильтры, статусы и CSV. В браузере проверены отправка обеих форм, появление записей в панели, заметки и скачивание CSV. Отдельно проверен реальный запуск через Gunicorn с записью и восстановлением после перезапуска. Сборка Docker-образа не проверялась: локальный Docker daemon выключен. Конфигурация Compose проверена; `nginx -t` нужно выполнить на целевом сервере.

Для статического просмотра на GitHub Pages используется отдельный экспорт `deploy/pages.py`: он не включает сервер и обращения. Команды и порядок публикации приведены в корневом [README](../README.md). Полный проект и экспорт Pages не заменяют друг друга.

Использованные серверные компоненты: [настройки Gunicorn](https://gunicorn.org/reference/settings/), [Gunicorn в PyPI](https://pypi.org/project/gunicorn/), [официальный образ Python](https://hub.docker.com/_/python). В `requirements.txt` разрешены исправления ветки Gunicorn 26, начиная с 26.2.0; установка и запуск проверены с 26.2.0 на Python 3.12.
